PROJECT JUSTIFICATION AND IMPACT
This project transcends the scope of a traditional web application by tackling the friction of modern knowledge management and the unreliability of current AI tools. The significance of this project is twofold: its practical value as a consumer product, and its academic value as an advanced engineering challenge.
Product Impact for Users: Eliminating the "Friction of Thought"
From Passive Chat to Active Operator: Unlike standard AI chatbots that only generate text, this system acts as an agentic partner. Users dictate natural commands, and the AI actively manipulates the workspace—updating notes and populating spreadsheets in under 4 seconds.
Bridging Notes and Databases: It eliminates the cognitive load of switching between unstructured brainstorming and rigid data entry. Users can speak their intent, and the system handles the complex formatting automatically.
Zero Data Anxiety: By enforcing a strict "Human-in-the-Loop" confirmation gate (visual diffs and ghost rows), the system ensures AI only suggests actions. The user retains absolute control, completely eliminating the fear of AI corrupting personal data.
Educational & Engineering Impact 
Building this platform required solving production-grade challenges, pushing the student's technical capability far beyond basic CRUD operations:
Decoupled Microservice Architecture: Mastered the design of strict, versioned API contracts to seamlessly bridge a TypeScript/Next.js frontend with a stateless Python/FastAPI backend.
Deterministic AI Engineering: Solved the notorious "AI hallucination" problem. By utilizing dynamic, runtime Pydantic schema generation, the system mathematically forces Large Language Models to output valid database structures, ensuring 100% data integrity.
High-Availability & Fallback Routing: Engineered a multi-model routing system via LiteLLM. If primary services fail, the system automatically falls back (Deepgram → Groq, Gemini → Groq(Llama model)) while maintaining the strict sub-4-second latency SLA and a low operational cost.
Prompting Security (Sentinel Layer): Designed and implemented a proactive prompt security layer using randomized cryptographic delimiters to detect, classify, and block malicious prompt injection attacks before they reach the core logic.
PROBLEM DOMAIN
As digital information accelerates in the modern knowledge economy, students and young professionals face unprecedented challenges in organizing, retrieving, and utilizing information. Research shows that information overload directly impairs knowledge acquisition (Feroz, Zulfiqar, Noor, & Huo, 2022) and that traditional personal knowledge management (PKM) methods are increasingly insufficient, often becoming “landfills of half‑baked notes” (Silveira, 2026). The cognitive cost of context switching is severe: over 97% of people lose productivity when switching between fragmented tools (Velumyan, 2026).
Concurrently, the industry is shifting toward AI and speech‑to‑text (STT), yet current implementations remain underutilized. Most AI assistants are passive chatbots rather than agentic partners capable of executing workspace operations (Nazeer, Sumbal, & Sultana, 2023). Manual keyboard input—averaging 40–60 words per minute—remains the primary bottleneck, while conversational speech reaches 125–150 words per minute, offering a 3x throughput advantage with lower cognitive load (Dhakal, Feit, Kristensson, & Oulasvirta, 2018).
A clear, research‑backed need exists for a comprehensive platform that mitigates context‑switching penalties by uniting unstructured text, structured databases, and low‑latency multimodal input (voice and text) into a unified, user‑centric system. The Multimodal AI Notetaking System is envisioned as this solution—an integrated workspace optimized for modern PKM, featuring Markdown editing, schema‑driven data tables, and an agentic AI assistant capable of securely interacting with user data.
EXISTING SYSTEMS


In recent years, the personal knowledge management (PKM) and productivity software market has matured considerably. Widely adopted platforms such as Notion, Obsidian, Roam Research, and Evernote serve foundational roles: capturing text, organizing hierarchical or networked thoughts, and, in some cases, managing relational data. Collectively, they have shifted the paradigm from static word processing toward interconnected “second brain” methodologies (Nazeer, Sumbal, & Sultana, 2023).
Yet despite their robust capabilities, existing platforms exhibit critical shortcomings in multimodal interaction and agentic automation. A notable challenge is the steep barrier to entry for structured data management. While tools like Notion offer powerful database functionalities, the need to manually configure schemas, apply filters, and enter tabular data constantly interrupts creative flow. User reports indicate that mastering Notion’s relational databases can take weeks of deliberate practice, with some users abandoning the tool entirely before eventually returning (Notion User Survey, 2024). This phenomenon illustrates how the promise of flexibility can paradoxically create overwhelming complexity (Li, Radev, & Rafiei, 2024).
Furthermore, while modern platforms have begun integrating AI, these implementations remain structurally limited. Current AI features are typically siloed into generative tasks (e.g., “summarize this text”) rather than operational tasks that execute concrete workspace operations (Nazeer et al., 2023). AI agents embedded in cloud‑based PKM apps often operate as passive chatbots rather than proactive teammates capable of interacting with user data (Basic Memory Blog, 2023).
Moreover, users cannot naturally converse with these systems to execute application‑state changes – for instance, saying “Add a new row to my Marketing Budget table for $500” and having the system safely map that voice command to a strict database schema. Speech‑driven querying of structured data is technically challenging, requiring either high‑quality automatic speech recognition (ASR) or novel end‑to‑end architectures (Song, Wong, & Zhao, 2024). Cascade approaches (ASR → text‑to‑SQL) suffer from error compounding, while more integrated solutions remain rare (Li et al., 2024). One user study found that speech‑driven query specification could achieve an average speedup of 2.7× compared to typing – but only when the system could directly map commands to database schemas (Ullauri, Paudel, & Prasad, 2020).
Relying on external voice‑to‑text tools (such as Otter.ai or built‑in OS dictation) only compounds the problem. These tools excel at transcription but lack workspace context or database awareness. A comprehensive review noted that Otter’s knowledge is limited to what it hears in meetings, completely disconnected from documents, wikis, or past support tickets. This lack of contextual understanding means that a spoken command like “find my budget spreadsheet” cannot be mapped to a specific database schema.
Finally, emerging research in spoken language understanding has demonstrated that achieving low‑latency voice‑driven productivity is feasible. New end‑to‑end architectures, such as the PRoDeliberation model, achieve latency reduction of 2‑10× over autoregressive models while retaining the ability to correct ASR mistranscriptions (Le et al., 2024). On‑device speech‑to‑text solutions now report latencies as low as 120 milliseconds, independent of cloud round‑trips (Dhakal, Feit, Kristensson, & Oulasvirta, 2018). These technical advances position voice‑driven AI as a near‑term viable interface for database‑aware workspaces, provided that the system is designed with both schema awareness and a “human‑in‑the‑loop” confirmation gate.
Recognising these systemic limitations, the Multimodal AI Notetaking System is proposed as a novel approach. It seeks not only to incorporate the core strengths of existing markdown editors and database tools but also to resolve their friction points. By offering schema‑aware AI, deterministic function‑calling, sub‑3.5‑second voice processing, and a strict “human‑in‑the‑loop” confirmation gate, the system provides a flexible, highly extensible architecture designed for the future of voice‑driven productivity.
The current enterprise market offers users with  a variety of productivity tools with different spec flavours to satisfy anyone, there’s 2 most popular when it comes to the PKM fields: Notion and Obsidian. The comparison below will show what the difference and who tends to choose what, between the standing giants and a newcomer.
Notion: 
Notion is an all-in-one workspace that combines documents, wikis, databases, projects, and calendars in a single platform. It uses a proprietary block-based editor (not plain Markdown) that allows rich content embedding, including databases, kanban boards, calendars, embeds, and more. Notion is known to be  moving toward AI autonomy agents that run on schedules, respond to triggers, and take actions without waiting for the user. This is powerful for teams but requires trust.
Obsidian 
Obsidian is a local-first, Markdown-based knowledge management tool built around the concept of linked notes and a visual graph. It stores all notes as plain .md files on the user's device, ensuring complete data ownership and portability. The desktop’s complete offline first design leaves AI entirely to the plugin ecosystem. The quality and safety of AI features depend on which third-party plugin the user installs.
Lock In - my application
A full-stack Next.js application that combines traditional Markdown notetaking with agentic AI capabilities, real-time voice transcription, task management, calendar scheduling, and structured data tables (Stacks). The app is designed as an academic/capstone project targeting power users who want unified workspace tools with AI assistance. It takes a middle path: AI is deeply integrated and context-aware, but every proposed mutation must be reviewed. The user is always the final decision-maker. This is a deliberate design choice rooted in the thesis research: exploring how agentic AI can participate in productivity workflows without removing human oversight.

Product Comparison: files.md vs Markdown Notes App

Data Ownership Storage Model
files.md stores everything as plain .md files on the user's local device, with optional sync via iCloud, Dropbox, or a self-hosted Go binary. There is no proprietary format. Files open in any editor today and will continue to do so indefinitely.
My product stores notes, stacks, tasks, and calendar data in a PostgreSQL database via Prisma ORM, with a structured in-memory cache in Zustand. This enables rich relational querying and cross-entity linking, but data portability requires a dedicated export pipeline that has not yet been implemented.

AI Integration Depth & Approach
files.md treats AI as an external reader of flat files, not a system component. The codebase is intentionally kept small enough for an LLM to extend on demand. There are no built-in AI features users bring their own workflows and prompts, keeping the AI surface area at zero.
My product treats AI as a core product layer. Voice input via Deepgram real-time STT feeds an NLU pipeline in FastAPI that parses intent, dispatches structured actions, and applies optimistic mutations to the editor. This is a strong differentiator and a significant maintenance surface that competitors without it must invest heavily to replicate.

Codebase & Scale Architecture
files.md was built by a single developer over five years with a strict philosophy of removing code rather than adding it. No build system is required the app runs by opening a plain HTML file. The Go server ships as one binary. It is explicitly designed to remain comprehensible to one person or one LLM context window, indefinitely.
My product is built on a multi-layer stack: a Next.js frontend, FastAPI microservice, PostgreSQL, Zustand state management, Milkdown editor, and Deepgram for STT. Each layer multiplies capability but also multiplies maintenance cost, onboarding time, and failure surface. Scaling this product requires a team rather than a single contributor.
The core tension: files.md optimizes for longevity and ownership; my project optimizes for capability. Neither is wrong, but they're solving different problems
